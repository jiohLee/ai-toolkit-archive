## 1. 기본 원칙

### 1.1. 문체

- 글의 종류별 문체
  - "~합니다"체: 대화 답변
  - "~한다"체: 문서. 사용자가 독자를 고려하여 지시한 경우에는 "~합니다"체 사용.
  - 명사 또는 명사형 어미(~함, ~임): 커밋 메시지, PR 제목과 본문, Azure Boards work item의 설명과 코멘트
- 한 글 안에서 문단의 문장은 한 가지 문체로 통일. 목록, 표, 그림의 문체는 `korean-structure-guide.md` 1.2 참조.
- 문서는 종결 어미뿐 아니라 어휘도 문어체로 선택. 일상 동사 대신 한자어 동사 사용(2.14절).
- 구어체 표현과 번역체 표현은 지양. 대표적인 번역체 표현은 불필요한 피동형(2.6절)과 행위를 명사로 묶은 문장(2.13절).

### 1.2. 용어

- 학술, 과학, 공학 용어가 문서에 처음 등장하면 영문 용어와 약어 병기.
  - 형식: `**국문 용어**(영문 용어, 약어)`. 앞의 국문 용어만 굵게 표시하고, 약어가 없으면 생략.
  - 예: **대규모 언어 모델**(Large Language Model, LLM), **하네스**(harness)

### 1.3. 문장 부호

- 나열에는 가운뎃점(`·`) 사용 금지.
- 따옴표와 낫표는 국립국어원 문장 부호 규정 준수.
  - 큰따옴표(`""`): 말이나 글의 직접 인용. 예: 실제로 던진 질문, 검색어, 답변 원문
  - 작은따옴표(`''`): 인용한 말 안의 인용한 말, 마음속으로 한 말. 특별히 강조할 부분에도 사용 가능.
  - 홑낫표(`「」`): 소제목, 작품 제목, 규정 이름 같은 제목. 작은따옴표로 대체 가능.

## 2. 문장 작성 원칙과 예시

- 예시의 `-` 줄은 Bad, `+` 줄은 Good.

### 2.1. 필수 문장 성분을 생략하지 않는다

- 주어(~은/는/이/가), 필수 부사어(~에게), 목적어(~을/를)의 생략 금지.
- 기술 문서에서는 누가, 누구에게, 무엇을 하는지 명확히 표현.

```diff
- 사용자의 추가 발화에 대기하기 위해 Recognizer.Expect Speech Instruction을 전송한다. 수신이 완료되면 모든 응답을 종료한 후 다시 발화 대기 상태로 전환한다.
+ 사용자의 추가 발화에 대기하기 위해 KVS는 Recognizer.Expect Speech Instruction을 Service Agent에 전송한다. Service Agent는 Recognizer.Expect Speech Instruction을 수신하면 모든 응답을 종료한 후 다시 발화 대기 상태로 전환한다.
```

### 2.2. 주어와 서술어를 호응시킨다

- 주체와 행위, 주체와 상태, 주체와 속성의 관계를 올바르게 표현.
- "~이유는"으로 시작한 문장은 "~때문이다"처럼 이유를 나타내는 서술어로 종결.
- 주어의 명사를 서술어에서 반복하는 것은 금지. 주어가 하는 일을 서술어로 표현.

```diff
- 카카오워크가 편리한 비즈니스 메신저인 이유는 카카오톡과 UI가 비슷하다.
+ 카카오워크가 편리한 비즈니스 메신저인 이유는 카카오톡과 UI가 비슷하기 때문이다.
```

```diff
- 이 시스템은 사내 직원이 회의실을 예약하는 시스템이다.
+ 이 시스템은 사내 직원이 회의실을 예약할 수 있도록 한다.
```

### 2.3. 수식어는 수식받는 말 바로 앞에 둔다

- 수식어와 수식받는 말 사이가 멀면 수식 대상이 불분명.

```diff
- 복잡한 소프트웨어의 설치 과정
+ 소프트웨어의 복잡한 설치 과정
```

### 2.4. 부사어와 서술어를 호응시킨다

- "절대로", "결코"는 부정문과, "반드시"는 긍정문과 호응.

```diff
- 다음의 사항을 탈퇴하기 전에 절대로 확인하라.
+ 다음의 사항을 탈퇴하기 전에 반드시 확인하라.
```

### 2.5. 조사를 올바르게 사용한다

- 문맥상 불필요한 조사는 삭제.
- 영어 단어 뒤에는 영어 발음에 맞는 조사 사용. 예: Writing(라이팅)은
- 괄호가 있으면 괄호를 무시하고 괄호 앞 단어에 맞는 조사 사용.

```diff
- SDK를 초기화를 한다.
+ SDK를 초기화한다.
```

### 2.6. 능동형 문장을 작성한다

- 피동형 문장은 한국어 문장이 번역체로 읽히는 주된 원인.
- 사람이 하는 행위는 사람을 주체로 표현. 무생물을 주어로 내세운 피동형이나 사동형 문장은 지양.
- "~에 의해 ~되다", "~되어지다" 같은 번역 투 표현도 같은 이유로 지양.

```diff
- [승인] 버튼이 클릭되어야 결제 승인이 완료된다.
+ [승인] 버튼을 클릭해야 결제 승인이 완료된다.
```

```diff
- 로그인이 되어야 설정 페이지로 이동될 수 있다.
+ 로그인을 해야 설정 페이지로 이동할 수 있다.
```

```diff
- 이 설정은 관리자에 의해 변경되어질 수 있다.
+ 관리자는 이 설정을 변경할 수 있다.
```

### 2.7. 이중 부정 대신 긍정형 문장을 작성한다

- 이중 부정의 문제: 문장 길이의 증가, 독자의 추가 해석 부담
- 부정형 문장도 가능하면 긍정형으로 변경.

```diff
- 휴게 시간은 소정 근로시간에 포함이 안 되지는 않는다.
+ 휴게 시간은 소정 근로시간에 포함된다.
```

```diff
- 대상이 아닌 유저에게 보상을 지급하지 않는다.
+ 대상인 유저에게만 보상을 지급한다.
```

### 2.8. 지시 대상을 분명히 밝힌다

- 대명사나 생략의 문제: 독자가 지시 대상을 찾기 위해 앞 문장으로 돌아가야 하는 부담
- 대명사 대신 대상의 이름을 다시 명시. 같은 종류의 대상이 여럿이면 어느 대상인지 명시.

```diff
- a는 b와 비슷한 개념이다. 그것은 c와도 비슷하다. 하지만 유사도로 치면 이전과 더 비슷하다.
+ a는 b와 비슷하다. a는 c와도 비슷하다. 하지만 유사도로 치면 a는 b와 더 비슷하다.
```

```diff
- 서버에서 온 요청을 받아 고객사 서버로 전달한다.
+ 카카오 i서버에서 온 요청을 받아 고객사 서버로 전달한다.
```

### 2.9. 모호한 표현 대신 구체적인 수치를 사용한다

- "조금", "잠시", "많이", "꽤"처럼 여러 해석이 가능한 표현 대신 수치 사용.

```diff
- 서버가 생성되기까지 많은 시간이 소요된다.
+ 서버가 생성되기까지 3, 4분이 소요된다.
```

### 2.10. 하나의 뜻에는 하나의 표현만 사용한다

- 같은 대상은 글 전체에서 같은 단어로 지칭.
- 같은 용어의 표기는 문서 전체에서 일관되게 유지.

```diff
- 고사양 게임을 하기 위해 고사양 본체가 필요하다.
- PC 정보를 파악하려면 CPU-Z, GPU-Z같은 컴퓨터 정보를 볼 수 있는 시스템 소프트웨어 유틸을 사용하면 된다.
+ 고사양 게임을 하기 위해 고사양 PC가 필요하다.
+ PC 정보를 파악하려면 CPU-Z, GPU-Z같은 PC 정보를 볼 수 있는 시스템 소프트웨어 유틸을 사용하면 된다.
```

### 2.11. 문장을 짧게 나눈다

- 문장을 잇는 연결 어미("~하는데", "~지만", "~어서")를 기준으로 긴 문장 분리.
- 미사여구와 불필요한 형용사 축소.

```diff
- 기계식 키보드는 브랜드 선정에 앞서 축을 선택하고 브랜드를 고르게 되는데 대표적인 브랜드로는 필코나 레오폴드, 바밀로 같은 키보드 브랜드가 있지만 그 외에도 매우 다양한 브랜드가 있어서 기계식 키보드를 선택한다면 개발자의 선택폭이 넓어지게 된다.
+ 기계식 키보드를 구매할 때는 브랜드보다 스위치 축을 먼저 선택해야 한다.
+ 축을 선택했다면, 브랜드를 선정한다.
+ 필코, 레오폴드, 바밀로 같은 브랜드가 대표적이다.
+ 그 외에도 매우 다양한 브랜드가 존재한다.
```

### 2.12. 맞춤법과 외래어 표기를 지킨다

- 맞춤법, 띄어쓰기, 오탈자 확인.
- 외래어는 국립국어원 한국어 어문 규범의 표기 준수.

```diff
- 어플리케이션, 비지니스, 컨텐츠, 콘트롤
+ 애플리케이션, 비즈니스, 콘텐츠, 컨트롤
```

### 2.13. 번역체 문장을 작성하지 않는다

- 번역체 문장: 영어 문장 구조를 그대로 옮겨 한국어로 읽으면 어색한 문장
- "A는 B의 C이다"처럼 행위를 명사로 묶어 서술하는 것은 지양. 행위의 주체와 동사를 살려 표현.

```diff
- 네 용어는 다음과 같이 구분된다. 이 구분은 이 문서의 정리이다.
+ 네 용어의 차이를 이 문서에서 정리하면 다음과 같다.
```

```diff
- 이 대응은 이 문서의 판단이다.
+ 이 대응은 출처에 없으며, 이 문서에서 정했다.
```

- 표나 그림을 주어로 내세운 "A는 B를 정리한 것이다" 형태는 지양. 내용을 주어로 두고 표나 그림은 서술어에 배치.

```diff
- Table 4는 SRS 1장의 절별 작성 요점을 정리한 것이다.
+ SRS 1장의 절별 작성 요점은 Table 4와 같다.
```

- "A의 B는 C 정도이다"처럼 속성 명사를 주어로 쓰는 것은 지양. 대상을 주어로 두고 동사로 서술.

```diff
- 상세설계의 작성 수준은 개발자가 문서만 보고 코딩할 수 있는 정도이다.
+ 상세설계는 개발자가 문서만 보고 코딩할 수 있는 수준으로 작성한다.
```

### 2.14. 문서에는 문어체 어휘를 사용한다

- 1.1의 "어휘도 문어체로 선택"을 구체화한 규칙.
- 문서에서는 일상 동사 대신 뜻이 분명한 한자어 동사 사용.
- 다음 구어체 어휘는 오른쪽의 문어체 어휘로 변경.
  - 구어 동사
    - 맡다: 담당하다
    - 고치다: 수정하다
    - 만들다: 구성하다, 생성하다
    - 적다: 기록하다
    - 붙이다: 부여하다
    - 넣다: 포함하다
    - 고르다: 선택하다
    - 더하다: 추가하다
  - 구어 표현
    - 깨지다: 성립하지 않다
    - 모아 보다: 분류하다
  - 보조 용언 "~해 두다": 삭제. 예: 저장해 둔 → 저장한
  - 줄임말
    - 앱: 애플리케이션
- 일상 동사 하나를 여러 뜻으로 사용하는 것은 금지. "쓰다"는 뜻에 따라 기술하다, 작성하다, 사용하다, 소비하다로 구분.
- 한자어 명사 뒤에 "진행하다", "실시하다"를 덧붙이는 것은 금지. 예: 검토를 진행한다 → 검토한다
- "목차 뒤에 개정 이력 표를 둔다"처럼 고유어 동사가 자연스러운 문장은 그대로 유지.

```diff
- 검토는 reviewer가 맡고, 결과는 스크립트가 만든 페이지에서 고친다.
+ 검토는 reviewer가 담당하고, 결과는 스크립트가 생성한 페이지에서 수정한다.
```

```diff
- 의견을 쓰는 데 출력 토큰을 3만 개 쓴다.
+ 의견을 작성하는 데 출력 토큰을 3만 개 소비한다.
```

```diff
- 범위에는 제품이 수행하는 일과 수행하지 않는 일을 함께 쓴다.
+ 범위에는 제품의 포함 범위와 제외 범위를 함께 기술한다.
```
